摘要

Forge Contract System 是 Forge 的知识基础设施层，为上层 Agent 提供结构化的 ABACUS 输入/输出/工件/科学量契约元数据。它由四个模块组成：M1（契约知识库）、M2（契约发现 API）、M3（契约验证框架）和 M4（契约查询服务）。该系统使 Forge 从"能执行 ABACUS 计算"升级为"能解释 ABACUS 计算契约"，是 Paimon v1.3 Agent 推理的知识基座。

动机与问题

问题影响
Agent 无法从 Forge 推理"计算带隙需要什么 ABACUS 输入"每次新任务需要人工查文档
ABACUS 上游变更影响面不可评估只能 reactive 修 break
Capability 之间的依赖关系（band 依赖 SCF）未声明上层 workflow 不知道执行顺序
同一物理量的多格式等价关系（TOTAL ENERGY = !FINAL_ETOT_IS）未声明等价关系只在覆盖链代码中隐式存在
指标单位不完整（仅 fermi_energy 有 _metric_units）上层无法做量纲一致性检查
Forge 覆盖边界不明确（哪些 ABACUS 输出是有意不覆盖的）维护者和 Agent 不知道边界在哪

M2: 契约发现 API

扩展现有 discovery.py 的两个函数，使 Agent 能从 CLI/API 获取完整契约元数据。

capabilities_document() 扩展

每个 capability entry 新增 contracts 字段（向后兼容，不影响现有消费者）：

  "name": "band",
  "maturity": "experimental",
  "operations": ["postprocess"],
  "contracts": {

    "input_defaults": {},
    "prerequisites": ["scf"],
    "metrics": {
      "band_gap": {"unit": "eV", "kind": "reported"},
      "fermi_energy": {"unit": "eV", "kind": "reported"}

    "artifacts": ["BANDS_*.dat"],
    "abacus_source": "source/source_io/module_parameter/input_parameter.h#calculation"
  }
}

request_schema_document() 扩展

每个 operation 的 request schema 新增 contracts 字段，携带该 operation 涉及的 ABACUS 参数元数据。

M4: 契约查询服务

新增 typed operation forge.contract.query（Phase C，在 M1–M3 稳定后实施）。这不是一个 ABACUS 计算 operation，而是一个元数据查询 operation。

查询类型

query_type输入输出用途
get_capabilitycapability name该 capability 的完整契约Agent 设计计算前查询
get_metricmetric nameunits, markers, 使用该指标的 capabilities上层做量纲检查
get_impactABACUS marker/pattern受影响的 capabilities + metrics上游变更影响评估
get_dependenciescapability nameprerequisite 闭包图workflow 排序
get_out_of_scope（无参数）完整 out_of_scope 列表 + 理由边界确认

边界约束：M4 是数据查询，不是科学推理。它返回结构化契约事实（"band 依赖 scf"），不做科学建议（"你应该先跑 SCF"）。科学推理由上层 Agent 基于 M4 返回的事实自行完成。

上游感知边界

Forge Contract System 不包含独立的"ABACUS 开发 Agent"。其上游感知策略为：

层次职责归属
ABACUS 物理功能开发（DFT 求解器、赝势方法、新算法）开源社区全权负责abacus-develop 仓
ABACUS 接口契约变更检测M3 一致性测试 + real-smoke gates 自动检测Forge 仓
变更影响评估M4 get_impact 查询：标记 → 受影响 capability/metric 列表Forge 仓
上游 issue 辅助起草薄脚本：从 M4 查询结果生成结构化 issue 模板（非 Agent）可选，按需
Forge parser 适配扩展 regex pattern + 更新知识库 markersForge 仓
生态需求向上游表达知识库 out_of_scope 节作为需求文档基础按需

ABACUS 开发 Agent 边界

Forge 不需要成为 ABACUS 开发 Agent，但 Contract System 是 ABACUS 开发 Agent 的知识基座。

三个层级的判断：

  • L1: 契约数据暴露（M1+M2） — Forge 内。Agent 可获取结构化的 capability → INPUT → OUTPUT → metric → unit 映射。这是 Forge 作为"Agent 可消费基座"的职责。
  • L2: 契约查询（M4） — Forge 内。确定性结构化数据查询（"查表回答问题"），不涉及科学推理。
  • L3: 科学计算设计助手 — Forge 外。Agent 问"我想计算 Si 的带隙"→ 系统返回完整 INPUT + workflow plan。这是科学推理，属于 Paimon adapter 或独立 Agent 层。

迁移与发布

  1. Phase A（M1 + M3）：编写 io_contracts.json 首版；编写一致性测试；默认门禁通过。
  2. Phase B（M2）：扩展 capabilities_document() 暴露 contracts；API/CLI parity 测试。
  3. Phase C（M4）：实现 contract.query operation；CLI + Python API 暴露。
  4. 后续：每新增 capability/parser pattern 时同步更新知识库；上游 ABACUS 新版本发布时更新 abacus_source 锚点和 markers。

风险与开放项

  • 维护成本：由一致性测试在 CI 中强制，不依赖人工记忆。
  • ABACUS 源码锚点漂移：abacus_source 是文档性参考，失效不影响 parser 运行。
  • M4 与 Forge typed operation 的关系：M4 是元数据查询 operation，不是 ABACUS 计算 operation。它的 request/result schema 需要独立设计，可能引入新的 operation type（区别于 ABACUS 相关的 prepare/execute/collect 等）。具体 schema 在 M4 PLAN 中确定。
  • 与 v1.2 知识库的关系：v1.2 的 Openknowledge RAG 系统服务 Agent 科学问答（不同用途）。Contract System 服务工程推理（本 SPEC 范围）。两者互补，不替代。
