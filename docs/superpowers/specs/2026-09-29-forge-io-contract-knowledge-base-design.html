摘要

Forge 的 native parser 当前通过分散在 prepare_profiles.py、collectors/abacus.py、collection.py 和 pyatb.py 中的 regex 和逻辑实现了 ABACUS I/O 契约的消费，但缺乏一份结构化知识资产来回答：计算某个科学量需要哪些 ABACUS 输入参数、产生哪些输出标记、解析为哪些 Forge metric、单位和来源是什么。

本 SPEC 定义一份 machine-readable 的 I/O 契约知识库（JSON 文件），映射 Forge capability → ABACUS INPUT 参数 → 输出标记（含 ABACUS 源码锚点）→ 解析指标（含单位）→ 工件 → 科学量的计算工程语义。知识库由一致性测试验证与实际代码同步，并暴露给 capabilities_document() 和上层 adapter。

问题陈述

当前存在的具体缺口：

缺口示例影响
INPUT → 输出因果断裂out_band=1 导致 running log 出现 BAND GAP =——因果关系只存在于开发者隐性知识中Agent 无法推理"计算带隙需要什么输入"
SCF 前置依赖未声明band 和 dos 需要 init_chg=file（前置 SCF），但 capability descriptor 不声明此依赖上层 workflow 不知道必须先跑 SCF
单位体系不完整仅 fermi_energy 在 diagnostics 中记录了 _metric_units；其余指标单位隐含在 regex 的解析逻辑中上层 adapter 无法对指标做量纲一致性检查
工件语义未定义BANDS_*.dat 的列格式（k-path, energy, occupation）没有 schema 定义后处理工具无法可靠消费 Forge 工件
上游变更影响不可评估ABACUS 改变 !FINAL_ETOT_IS 格式时，不知道哪些 capability 受影响上游升级后排查成本高
同物理量多标记等价未声明!FINAL_ETOT_IS 和 TOTAL ENERGY = 是同一物理量（Kohn-Sham 总能量）的两种输出格式等价关系仅在覆盖链代码中隐式表达

关键字段约定

字段类型说明
unitstring必须属于 v1.2 CANONICAL_MACHINE_UNITS 集合
kindenumreported（regex 直接解析）| derived（从其他指标计算）
markerslist每项含 pattern（正则的文本描述）和 abacus_source（生成该标记的 C++ 源码位置）
requires_inputstring只有当 INPUT 中启用了某参数时才出现的输出
prerequisiteslist必须先完成的 capability（如 band 依赖 scf）
abacus_sourcestringABACUS 仓内的源码文件路径（可选行号），供上游变更追溯

消费者与 API

1. capabilities_document() 扩展

当前 discovery.py 的 capabilities_document() 只返回 capability 名称和 operation 列表。本 SPEC 将其扩展为可携带知识库元数据：

// 当前输出
{"schema_version": "forge.capabilities/v1", "capabilities": [{"capability": "scf", "operations": ["prepare","modify","execute","collect"], "maturity": "experimental"}, ...]}

// 扩展后（新增 contracts 字段，向后兼容）
{"schema_version": "forge.capabilities/v1", "capabilities": [
  {"capability": "scf", "operations": [...], "maturity": "experimental",
   "contracts": {
     "input_required": {"calculation": "scf"},
     "input_defaults": {"dft_functional": "pbe"},
     "prerequisites": [],
     "metrics": {"total_energy": {"unit": "eV"}, "fermi_energy": {"unit": "eV"}, "converged": {"type": "boolean"}}
   }
  }, ...
]}

Agent 通过 abacus-forge capabilities --json 获取扩展元数据，无需读源码。

2. Paimon adapter 消费

Paimon v3 的薄 adapter 在构造 tool 描述时，可从知识库生成 tool 的参数说明和返回值说明，而不是硬编码字符串。

3. 上游变更影响查询

当 ABACUS 上游改变某个输出标记（如 !FINAL_ETOT_IS 的格式变化）时，在知识库中搜索该标记即可确定哪些 capability 的哪些指标受影响。

上游变更跟踪

知识库中的 abacus_source 字段建立了 Forge 解析标记与 ABACUS 源码位置的映射。跟踪流程：

  1. ABACUS 发布新版本 → 用新版本运行 real-smoke gates → 如果某个指标消失，diagnostics warning 提示哪个标记未匹配
  2. 在 ABACUS 新版源码中搜索旧标记 → 找到变更位置 → 更新知识库中的 abacus_source 和 markers
  3. 在 _METRIC_PATTERNS 中添加新 pattern → 离线回归通过 → 知识库一致性测试通过

迁移与发布

  1. Phase A：编写知识库 JSON 首版（从现有代码提取全部 6 个 capability + common artifacts + convergence markers + input units）。
  2. Phase B：编写一致性测试 test_io_contract_consistency.py；确保全部通过。
  3. Phase C：扩展 capabilities_document() 暴露 contracts 字段。
  4. 后续：每新增 capability 或 parser pattern 时同步更新知识库；上游 ABACUS 新版本发布时更新 abacus_source 锚点和 markers。

风险与开放项

  • 维护成本：每新增 parser pattern 或 capability 时须同步更新知识库——由一致性测试在 CI 中强制，不依赖人工记忆。
  • ABACUS 源码锚点失效：上游重构可能移动输出标记的生成位置——abacus_source 是文档性参考，不是硬依赖；失效不影响 parser 运行。
  • 科学量映射范围：本 SPEC 只覆盖 Forge 已解析的计算工程事实（能量、力、应力、收敛等），不覆盖需要后处理计算的科学量（band gap 精确值需从 BANDS_*.dat 后处理计算，Forge 只记录 running log 中 ABACUS 报告的近似值）。后处理科学量的映射可在后续 SPEC 中扩展。
  • 与 capability descriptor 的关系：当前 capability descriptor（contracts.py 中的 CapabilityDescriptor）仅包含 name/operations/maturity；知识库的 contracts 扩展是补充而非替换。两者是否合并为单一 source of truth 留作后续决策。

本地 SPEC 是规范源；远程审阅副本如有，仅为非规范镜像。
